# Proposed Type authoring examples

These are authored examples of the draft [Type-definition Markdown format](../../specs/formats/markdown-type-definitions.md), not converter results, installed Types, fetched definitions or provider conformance. All `types.example` and `schemas.example` application identities and revision tokens are illustrative literal values. They establish no live Scope, registration/default selection, current owner, authority or publication. Actual intrinsic-2 metatype/Refines pins come from the selected source publication; mixing them with application examples does not qualify a provisioning operation.

| Input | Literal expected comparison value | What to review |
| --- | --- | --- |
| [Work item authoring](work-item.authoring.md) | [Authoring value](work-item.authoring.expected.json) | New Bead-Type definition intent, exact metatype and parent, open descriptor extension, optional/false/empty preservation, property access, participation and positive ownership. No definition revision or declaration ID/revision is invented. |
| [Reviewed reference authoring](reviewed-reference.authoring.md) | [Authoring value](reviewed-reference.authoring.expected.json) | New Link-Type definition intent with no assigned Type identity; exact metatype/parent, correlated endpoint pairs and family constraints. Its definition remains a Bead. |
| [Recorded work item](work-item.recorded.md) | [Recorded value](work-item.recorded.expected.json) | A separate illustrative exact definition snapshot with a complete captured Refines record, nominal owned grouping and omitted local propertiesSchema under intrinsic-2. It is not the executed result of the authoring example. |

[Work item properties](work-item-properties.md) delegates to the selected sibling Markdown schema v0.6 notation and its explicit format marker, with the entire expected projected schema embedded in the authoring value. That file is rendered through the sibling API; the historical v0.5 table syntax is not a second accepted parser mode. The Link-Type example uses the complete literal [properties schema](reviewed-reference-properties.schema.json) and [shared application resource](shared-fields.schema.json). Their `$id` values and relative `$ref` must survive exactly; the Type's still-unassigned identity and file paths cannot supply a schema base.

[Presence cases](presence-cases.json) make omission distinct from false, empty text, empty schema/map/array and explicit wildcard ownership. Duplicate participation rows are preserved, while duplicate ownership selectors refuse. [Malformed cases](malformed-cases.json) point to complete negative Markdown files and additional literal counterexamples with expected locations/codes. These are written Type-format expectations; a Type-format parser has not been implemented or executed. The delegated property-schema notation has its own bounded codec and projection checks.

Structural review can check the expected descriptor `properties` objects against the current intrinsic-2 category schemas. It can separately check literal common record/Reference shapes. Such checks cannot establish parent definitions' availability, registration, exact semantic conformance, accepted specialized Refines authority, matching ownership populations, actual recorded completeness or allocation/publication. The examples deliberately do not include a full accepted parent closure, so no positive Type-admission claim follows from their shape.

The [artifact checks](../../packages/protocol/src/markdown-type-artifact.test.ts) validate expected descriptor shapes, the recorded carrier, exact token syntax, local schema-resource references and the delegated schema projection. They do not execute a Type-format parser, provider, CLI, engine, installation or network operation. The format adds no general Type lifecycle commands and modifies no descriptor/profile/schema artifact.
