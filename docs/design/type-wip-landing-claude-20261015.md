# Merge blockers

**1. High — `specs/types.md:935` (§7 heading) vs `:970–1132`, `:1136–1145`**
`## 7. Decisions still needed` encloses §7.0–§7.3, three of which state *selected* design: `:972-974` ("There is no separate local activation/publish step"), `:1028` ("The following lifecycle distinctions are selected design"), `:1108` ("Selected direction:"). Meanwhile §8's readiness table has no row for the §7.2 origin/installed-identity/acquisition decisions or the §7.3 alias direction. Impact: the newly accepted registry/installation/alias decisions read as unresolved exactly where the next author checks what is settled — and the genuinely open items inside them (registration granularity, unpinned-write selection, alias root) read as settled. Fix: retitle §7 ("Lifecycle, distribution and open decisions"), put its two bullet lists under an explicit `### 7.4 Open decisions`, and add two §8 rows — one for §7.2 (selected; granularity + unpinned-write selection open) and one for §7.3 (direction selected; root/precedence/collision open).

**2. High — `specs/types.md:67` and `:507`**
"Explicit floating Type input resolves before commit" / "explicit floating author input resolves once before commit" is stated with no pointer to `:1093-1096`, where *which* revision an unpinned write selects is explicitly undecided ("a Scope-selected default versus the origin's current revision was proposed but not decided"). Impact: §2 and §4.2 are the sections a domain-spec author reads first; both present a resolved-sounding mechanism for a NOT-accepted decision, inviting a latest-resolution assumption baked into the Memory spec. Fix: append "(the revision-selection rule is undecided — see §7.2)" at both lines.

**3. Medium — `specs/schemas/README.md:144-147` vs `check_examples.py:145-154`**
The README claims the check verifies "exact example references". It resolves only affiliation pins, declaration `type` pins and declaration targets. Verified: setting `type`'s and `issue`'s `ownsOutgoing` revisions to `NO-SUCH-REV` **and** repointing `dependency`'s endpoint `types` URIs at a nonexistent Bead still passes all 95 cases. Impact: false assurance about the one property readers trust the foundation fixture for — internal pin consistency; a dangling pin can land unnoticed. Fix: either add ~5 lines after `:154` sweeping every `{uri, revision}` in the fixture and asserting membership in `by_pin`, or narrow the sentence to "affiliation and declaration-target references".

**4. Medium — `specs/types.md:171-173` (§2.1) and §5.7 `:760-779`**
Only `type` carries an `ownsOutgoing` declaration in the fixture (`type-foundation.json:254-263`), yet all eight definitions hold owned ConformsTo Links. That requires `ownsOutgoing` to be inherited through Bead-Type conformance — which the doc asserts only as a one-off ("BeadType and LinkType inherit this behavior") and never as a general rule, even though §5.1 `:541`, §5.2 `:596` and §5.8 `:789-791` do state inheritance for endpoint lists, bounds and acyclicity. The adjacent sentence ("A descriptor's own `ownsOutgoing` *instead* governs the instances it describes") implies two mechanisms where the fixture uses one. Impact: the Memory author cannot tell whether a Memory subtype inherits a base type's ownership of citation Links. Fix: add one sentence to §5.7 stating `ownsOutgoing`/`incoming`/`outgoing` are inherited conjunctively through Bead-Type conformance, and reword `:171-173` so Type's ConformsTo ownership is an instance of that rule, as encoded.
