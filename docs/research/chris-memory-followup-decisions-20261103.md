# Memory follow-up: deletion, CLI compatibility, History and Inception

Assessment date: 2026-11-03. This follow-up expands decisions Donna raised after the full [Chris Memory proposal assessment](chris-memory-proposal-bdp-assessment-20261103.md), evaluated against BDP commit `bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa`. It is a sourced design assessment, not a normative change or implementation claim.

## Executive findings

- The three generic deletion policies are distinct: refuse when incident Links exist; delete the target and all its incident Links; or recursively delete selected Beads along selected Link Type/direction axes. Chris R20 adds a fourth domain-specific policy: remove floating citations while preserving pinned ones. A CLI flag cannot create semantics the selected service contract forbids.
- CLI aliases can preserve familiar command names, but cannot by themselves reconcile command behavior, key storage, output formats or an unmigrated KV workspace. In particular, Chris’s “remember always writes” conflicts with the candidate’s bare-word recall safeguard; `recall --json` and complete JSON listings also need explicit decisions.
- BDP History has strong exact-read and retained-version guarantees when selected. The remaining gaps concern the Memory dependency on those promises, History plus recovery composition, atomic overwrite receipts, instant-start project change acquisition, retained-version erasure feed, retention holds and mandatory actor attribution.
- Polly’s October 17 Inception direction covers the lifecycle meaning well, but remains proposal-only and is not the same as Chris’s freely editable Memory field. Current Core schema cannot carry it yet; schema, CLI and Memory semantics still need reconciliation.


Assessment against BDP main at `bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa`. This is a design note, not a normative change. The underlying protocol must make deletion behavior explicit; CLI names can map onto that contract, but a CLI cannot manufacture graph semantics that the selected protocol forbids.

## Three deletion behaviors

| Proposed mode | Meaning that needs to be specified | Current BDP position | Assessment |
| --- | --- | --- | --- |
| Refuse if incident Links remain | Delete the Bead only if its live incident-Link set is empty; otherwise return a refusal without mutation. | This is the selected Write rule. Hidden incident Links are not disclosed by the refusal. Callers may explicitly remove known Links in the same atomic batch, but the final graph must have no live incident Link. ([Write § deletion](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/specs/profiles/write/write.md#L210-L219)) | Covered and safest default. It does not satisfy Chris’s Memory rule for deleting a target while retaining pinned citations. |
| Remove every incident Link with the Bead | Delete all incoming and outgoing Links incident on the target, then delete the target atomically. | Write permits explicit Link deletion and atomic batching, but does not define an implicit “all incident Links” delete mode or an exhaustive affected-Link receipt. Hidden Links also create an authorization/disclosure question. ([Write § deletion](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/specs/profiles/write/write.md#L210-L219); [Core § incident Links](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/specs/profiles/core/core.md#L905-L953)) | A coherent explicit policy, distinct from cascade. It removes pins as well as floating Links, so it is unsuitable when historical citations must survive. Define scope, atomicity, and what the result may disclose. |
| Cascade deletion | Delete the target and other Beads reached along selected Link types/directions, potentially recursively. | BDP has no general recursive-delete contract. Current deletion is one Bead plus explicit Link removals; graph traversal does not imply mutation closure. | Plausible core capability, but must be narrowly bounded. Require at least one `--type` or `--exact-type` selector as the user suggests; allow multiple selectors as a union. `--exact-type` should match only that nominal Link Type, while `--type` needs a precise conformance/descendant rule. Specify traversal direction, recursion/fixed-point, cycles, shared descendants, pinned endpoints, and treatment of unselected incident Links. Require preview and atomic all-or-none execution; refuse if authorization or finite bounds prevent proving the selected closure. |

“Remove all incident Links” operates on edges adjacent to one deleted node. “Cascade” also deletes selected neighboring Beads and repeats the process. These are different mutation closures and should not share an ambiguous `--cascade` meaning. A safe interface could retain ordinary `delete` as refuse-if-linked, offer an explicit detach-all-links mode, and reserve cascading for an explicit type-filtered preview/apply operation. The exact command and flags remain a product decision.

Chris’s Memory requirement is a fourth, domain-specific policy rather than either generic mode: on target deletion, remove in-Scope Links whose target Reference is `latest`, preserve pinned Links, version affected Memory sources, report removed Links and newly versioned sources, and do not restore removed Links when restoring the target. That is **not** ordinary edge detachment (it preserves pins) and **not** cascade (it does not delete other Beads). It is stated in proposal #5877 R20 and scenario S9; see [Chris’s proposal](https://github.com/gastownhall/beads/issues/5877#issuecomment-5787432078) and the [prior complete assessment, R20](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/docs/research/chris-memory-proposal-bdp-assessment-20261103.md#r20).

## Recommendation

Treat the three generic deletion modes as separate, explicitly named protocol policies. Keep refusal as the safe ordinary default. Specify detach-all separately. Add type-filtered cascade only with a defined closure and atomic preview/apply contract. Separately decide whether Memory gets its proposal-specific “remove floating, retain pinned” rule. Then map the four legacy CLI spellings to those settled shared operations, preserving aliases and outputs where possible while explicitly resolving the `remember`, `recall --json`, and `memories` semantic differences above.

This note isolates the History portion of the requirement-by-requirement assessment in [the full report](chris-memory-proposal-bdp-assessment-20261103.md). It evaluates a counterfactual in which a service implements every currently specified optional capability relevant to Memory, including complete Core History, Write, and Events. It does not treat a missing reference implementation feature as a specification gap.

## What BDP History already promises

When advertised, `historicalResolution` is a complete optional capability, not a promise inferred from storage. It covers Beads and Links, requires exact historical reads without substituting current or nearest state, and supports retained-version enumeration under a stable snapshot. Authorized deleted subjects can still have readable retained history. If a cited version is removed, the address must continue to report its substantiated Gone reason to an authorized History caller; that evidence has no expiry exception. Native versions under complete History must carry authority-observed `committedAt`, `agent`, and `message` change context. These are substantial guarantees. See [Core History discovery](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/specs/profiles/core/core.md#L1125), [immutable change context](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/specs/profiles/core/core.md#L1160), [exact historical reads](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/specs/profiles/core/core.md#L1197), [missing-state diagnoses](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/specs/profiles/core/core.md#L1278), and [retained-version pages](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/specs/profiles/core/core.md#L1348).

A useful precision: BDP's History change context requires commit time, agent, and message for native History versions, while the actor attribution remains optional and may truthfully be unknown. Chris's proposal asks for a responsible actor on each accepted change. That is a Memory conformance requirement BDP does not currently impose; History does not fill it in.

## Practical reading

BDP already gives a solid exact-history substrate, truthful absence/uncertainty states, and explicit erasure diagnoses. The proposal's remaining History issues are mainly composition and acquisition: requiring that substrate for Memory, resolving the joint recovery binding and latest-source policy, returning atomic overwrite context, and giving persistent mirrors an instant-start plus retained-version-removal feed. The actor requirement is another Memory-level rule; it is not a missing timestamp feature.

The concise History verdict in the full matrix is **partial**. Exact historical read, retained enumeration, and authorized Gone reasons are specified; History's use by Memory, recovery composition, richer write receipts, project change acquisition, and erasure synchronization are not fully specified.

**Assessment date:** 2026-11-03
**Scope:** Does Polly’s current Inception direction cover the Inception requirements in Chris Sells’s Memory Beads proposal?

## Finding

Polly’s design covers the central portable lifecycle meaning of Inception: it records how an identity’s current period of presence in a Scope began, distinguishes native creation, insertion by import, recovery by revert, and unknown history, and specifies preservation across ordinary edits and deletion. It is shared by Beads and Links rather than being Memory-specific.

This is an **accepted design direction recorded in a proposal**, not a landed BDP contract. The proposal says schema/CLI propagation is pending. Current Core does not admit an `inception` member, and its generated closed `revisionProvenance` schema has only `actor`, `agent`, `committedAt`, and `message`. So an implementation conforming to current canonical BDP cannot yet carry Polly’s field in the common envelope.

There is also a real semantic question against Chris’s text: Chris describes Inception as editable Memory state, where changing it creates a Memory version; Polly defines it as identity lifecycle context that ordinary updates preserve, with only identity re-entry setting a new value (`revert`). These can coexist if Memory exposes the current-period value and treats lifecycle transitions as the only permitted changes, but that restriction should be reconciled explicitly. Otherwise the two proposals imply different mutation semantics.

## Selected values and boundaries

The accepted October 17 decision receipt selects one shared open-enum field with values `create`, `import-insert`, `import-upsert` (only for a future upsert insert branch), `revert`, and `unknown`. Ordinary updates, live-to-live historical-base updates, and upserts of already-live identities preserve the value. Terminal deletion preserves it; deleted-to-live recovery sets `revert`. Unknown historical cause stays unknown. The enum does not require a CLI command with the same name, does not authorize adding upsert, and does not require signing, an import Activity, backfill, or migration.

The later #7510 body further says the existing update command should use `--from-revision TOKEN` for same-identity recovery rather than adding `bd revert`; protocol `fromRevision` is selected in #7719, while final CLI alias treatment and schema/runtime propagation remain work. Thus Inception’s `revert` value is a lifecycle label, not a command name.

## What remains to settle or implement

1. Amend the canonical Core envelope and closed JSON Schemas to permit and define `revisionProvenance.inception`, including whether the field is required on newly created resources and how unknown/imported legacy values are represented.
2. Reconcile Chris R3/R12’s “editable” language with Polly’s lifecycle-only update rules. State whether a caller can set Inception independently, or whether only create/import/recovery operations set it.
3. Define which current Memory structured reads and write results expose the value, and align CLI/Go/HTTP mappings; proposal direction alone does not provide those bindings.
4. Specify source mappings for migration/import and ensure values are preserved rather than inferred or defaulted. The `import-upsert` value remains conditional on a separately added capability.
5. Qualify the interactions with terminal deletion and same-ID recovery in the canonical service contract. The accepted direction describes them, but current Core schema does not encode them.
