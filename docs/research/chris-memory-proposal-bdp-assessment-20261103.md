# Chris’s Memory proposal against a fully implemented BDP

Assessment date: 2026-11-03. Advisory research; no specification decisions or implementation changes.

## Answer

**A fully implemented service and client following the current BDP specifications would not satisfy Chris’s entire proposal.** BDP provides a substantial substrate: stable identities, first-class Links, durable metadata, exact references, optional complete History, snapshot pagination, body-omitting projection, guarded writes, retry safety, atomic batches and explicit-source same-ID recovery. The remaining work includes actual semantic disagreements, unspecified Memory contracts and product integration duties. Finishing the current reference implementation alone would not close those gaps.

The clearest counterexamples are:

1. **Deletion:** Chris requires floating Links to be removed and pinned citations to survive deletion. Current Write refuses deletion while any live incident Link remains, including a pinned Link. An atomic batch cannot make surviving pinned Links legal under that rule.
2. **Names and commands:** Chris’s keys are optional, mutable names separate from identity, and `remember` always writes. The Memory CLI candidate equates `--key` with canonical `--id`, derives identity from content and retains a bare-word recall behavior.
3. **Versioned relationships:** Chris puts every outgoing Memory Link in the source’s versioned state. The Memory domain draft expressly makes direct References unowned. Editing one need not revise the Memory.
4. **History promises:** even granting complete History, its combination with historical Update still has an expressly unselected joint binding. Separately, the Memory Type does not require all the History capabilities Chris consumes as a condition of advertising Memory support. Ordinary mutation results do not guarantee the replaced version’s attribution or the richer current context on a stale-write refusal.
5. **Memory records and feeds:** editable Inception, derivation/completeness, a complete key inventory, mandatory responsible-actor attribution, expected/observed target state, instant-start project history and retained-version removal notifications lack the required bindings.
6. **Product and interchange:** migration, compatibility across CLI/Go/HTTP, selective prompt and bulk-output defaults, and selected connected-unit interchange need explicit contracts. Transfer has useful design direction but still has unassigned family codecs and wire bindings.

These are different kinds of work. Context-pack token budgets, ranking, deduplication, truth judgments and the Obsidian mirror itself belong to consumers; they are not missing BDP services. Their required source evidence and change acquisition do expose genuine protocol/domain gaps.

**Important positive correction:** BDP now has optional native Resource projection that can omit Memory bodies and metadata from inventory results. Common metadata and in-place Link repinning are also specified. Older discussion of their absence should not be carried forward unchanged. Projection does not compute excerpts, key matches or a lexical-search result contract.

## Scenario assessment

These are contract-level action traces, not executed tests. Client composition does not imply a transaction across separate calls or an atomic multi-Resource snapshot.


### S1 — Record durable knowledge without inventing a name

**Trace:** the Memory client derives a title from the supplied body, then calls advertised Create Bead without an ID, using the installed Memory Type and explicit title/body. It records the returned canonical ID and revision. Under full History it can obtain that revision's carried attribution/change context. A later explicit alias put can add or repoint a friendly locator.

**Division:** allocation and atomic Resource creation belong to Core/Write; title derivation, no automatic key, empty-body distinction, Inception/derivation fields and the Memory authoring contract belong to the Memory product. Types can enforce an installed descriptor; BDP has no portable Type-install operation. Alias paths are not arbitrary opaque legacy key strings, and there is no general “list every key of this Memory” operation. Rev4 Open question 1 still needs resolution; alias put is separate from creation and does not version the Bead.

**Status:** basic creation is composable; complete key/Inception/derivation behavior needs a selected product model. No atomic Bead-plus-alias claim. [Write: allocation, line 185](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/specs/profiles/write/write.md#L185); [Core: aliases, line 136](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/specs/profiles/core/core.md#L136); [Types: capability, line 89](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/specs/profiles/types/types.md#L89); [Core: immutable change context, line 1160](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/specs/profiles/core/core.md#L1160).

### S2 — Search, recall, then improve the existing Memory

**Trace:** discover a Memory inventory using current List filtered by its installed Type. For title/ID summaries use projection; for Rev4 body substring matching, a trusted client must explicitly acquire bounded full records or use a separately specified Memory search facility. It renders deterministic compact matches with selected revision addresses, then explicitly GETs the selected current/exact Resource. Edit that ID with `expectedRevision` and idempotency, reconciling a conflict rather than silently creating a duplicate.

### S3 — Forget, retain exact citations, then restore

**Trace possible today in the contracts:** delete an unlinked Memory through ordinary Write; full History can subsequently read retained exact editions. Separately, historical-update can use a retained source revision plus an independently guarded deletion terminal to restore the same ID as a new version, preserving current structural rules and not reviving old Links.

**Missing steps:** the requested linked deletion cannot proceed: current Write refuses it. Explicitly deleting floating Links first can approximate retirement, but must also remove pinned incident Links, violating Rev4. Optional atomic batch can remove a bounded known Link set and the Bead together, but cannot leave the forbidden pinned graph; an intervening unknown Link may cause refusal. Moreover full History and historical-update cannot currently be jointly advertised on the same Scope.

**Status:** genuine shared-contract/composition gaps, not missing CLI sugar. Retention is policy-dependent; pins do not hold content forever. ### S7 — Concurrent edits and non-silent overwrite

**Trace:** both clients GET R1. A writes with expected R1 and receives R2. B's expected-R1 edit fails with no effect; B can GET a newer current Resource, compare exact retained R1/R2, merge and retry with a fresh guard. An unguarded edit may atomically replace whatever is current; History can expose retained versions for later comparison. Identical durable state remains a no-op regardless of different attribution input.

**Missing guarantees:** Rev4 requires the mismatch result to carry the actual current revision and attribution, and an unguarded success to carry the actual replaced revision and attribution. Ordinary result/Problem contracts do not promise these. Follow-up GET is another observation; it can race. History predecessor relations help when known, authorized and retained, but are not an unconditional atomic predecessor receipt. Retention policy also qualifies “nothing lost”; not an infinite-retention guarantee.

**Status:** guarded no-lost-update and retained comparison are achievable; the complete Rev4 diagnostic/result contract is a gap. [Write: covered state and guards, line 707](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/specs/profiles/write/write.md#L707); [attribution/results, line 771](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/specs/profiles/write/write.md#L771); [Problems, line 1019](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/specs/profiles/write/write.md#L1019); [Core: historical relations, line 1409](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/specs/profiles/core/core.md#L1409).

**Trace:** install/register appropriate Type definitions outside ordinary protocol CRUD; create Task→Memory and Memory→Memory Links, retain returned Link IDs, enumerate without fetching target bodies, then delete one by its Link ID. For Rev4 semantics, the provider must declare the Memory's outgoing Link families owned. The source's revision then changes atomically with that Link, while the target's revision does not. ### S9 — Floating deletion versus surviving pinned citation

**Required trace:** delete the live policy, atomically remove/report its latest-following Task Link, but retain the Memory's pinned Link to a deleted supporting Task and continue resolving that exact retained target with honest deletion information.

**Actual contract:** either target's incident Link blocks native deletion. Deleting the Link first loses precisely the pinned live citation Rev4 requires. Atomic batch does not change the final native graph constraint. Exact historical reads can truthfully resolve retained editions and expose authorized historical context, but ordinary current GET alone does not promise to distinguish hidden/never-existing from deleted; deletion disclosure is authorization-sensitive.

**Status:** genuine deletion-policy mismatch. A product cannot claim this scenario by calling a current native delete and handling a refusal, or by replacing pinned Links with unrelated metadata. Readiness remains product-owned. [Write: incident-link refusal, line 210](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/specs/profiles/write/write.md#L210); [Core: reads after deletion, line 878](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/specs/profiles/core/core.md#L878); [historical lifecycle boundary, line 1229](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/specs/profiles/core/core.md#L1229).

### S10 — Pins, outgoing captures, bounded incoming views

**Trace:** resolve an unpinned URI through current GET; resolve a pin through exact historical GET. Preserve that literal Reference when the target changes. Read an exact source Resource's saved owned-Link capture for its historical outgoing view. Enumerate incoming Links through the native bounded incident view, following its continuation and reporting its authorization-relative completeness.

**Division:** stable revision identity, truthful historical refusal and owned-capture semantics are BDP. The installed ownership declaration determines which outgoing Links belong to the historical source. Incoming completeness is not a claim about hidden Links or a global graph snapshot. A current incoming view is not automatically an as-of historical incoming graph.

**Status:** achievable for the specified retained/authorized editions under compatible ownership; current v0.2's unowned References need reconciliation with Rev4's *whole* outgoing historical plane. Pins do not prevent pruning/erasure. ### S11 — Lossless, interruption-safe legacy conversion

**Trace:** a product migrator inventories every supported legacy reader/writer, validates each key/body including empty bodies, derives titles, allocates canonical IDs, and records truthful unknown legacy authorship/derivation rather than inventing it. It stages canonical Resources and a chosen key mapping, validates counts/content/collisions, then switches all surfaces through one recoverable visibility boundary. Interrupted states expose usable old data, complete new data, or an inspectable unavailable migration state.

**Division:** normal attributed Create and optional bounded batch support pieces. Legacy database access, cutover, recovery and compatibility frontends are product/admin work. BDP has no generic legacy-store migration endpoint. Aliases are not batch members, and normal CRUD cannot import arbitrary original revisions/provenance. A series of successful creates plus retries does not prove atomic public cutover.

**Status:** achievable by a deliberately engineered product migration; not established merely by fully implementing portable BDP. Key storage and truthful representable legacy-history policy remain prerequisites. [Write: allocation, line 185](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/specs/profiles/write/write.md#L185); [aliases, line 841](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/specs/profiles/write/write.md#L841); [batch members, line 1109](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/specs/profiles/write/write.md#L1109); [Core: historical import assurance, line 1443](https://github.com/gastownhall/bdp/blob/bd3c296d51b3d1179d7487a591f2bb7b7fca0bfa/specs/profiles/core/core.md#L1443).

### S13 — Connected, identity-safe interchange

**Required trace:** select Tasks/Memories/Links, obtain a coherent interchange unit including selected endpoint/history meaning, validate destination mappings and collisions, then atomically publish the connected unit or reject it. Never resolve identity by a human key or similar-looking ID.

**Status:** shared interchange requirement remains open; neither client sequencing nor an empty “Transfer supported” label proves it. Rev4 itself explicitly says no shipped path yet satisfies R27. ### S14 — Public viewer and independent quality tool

**Trace:** discover/read current projected summaries, selected full Resources, exact historical editions, per-Resource version pages, owned historical Links and bounded incident views. ## Does current Memory v0.2 materially differ from Chris's Rev4?

**Yes.** Both use durable knowledge Beads, explicit graph relationships and external judgment. The current catalog is nevertheless a materially different and expanded design, not merely Rev4 encoded as Types.

## R6 — Compact deterministic discovery

**Positive selected projection composition:** C “Optional Resource projection”1537–1672 is CURRENT canonical optional protocol, not a historical stub and not a runtime gap. This is a genuine portable body-free browse building block, with exact revision available for a pin and optional recorded attribution. It requires full-edition authorization before masking and does not expose otherwise hidden records. It does not COMPUTE an excerpt, key-match provenance, a Memory key list, or case-insensitive body substring membership. Those remaining requirements need a bound domain operation or explicit client/product composition; a mask cannot invent new values or add a lexical search operator. Existing native Selector can compose supported equality/order/existence predicates, not arbitrary substring functions.

## Decisions the final report should expose

1. **Shared graph lifecycle:** adopt Chris's floating-cascade/pinned-survival rule or retain current incident refusal. This changes Core/Write/History/authorization/public results and cannot be achieved by implementing today's spec more completely. Hidden sources make “list every removed Link” need an explicit nondisclosure policy.
2. **Ownership and vocabulary:** every outgoing Memory Link versus current unowned References/selective ownership; Memory-compatible related/custom definitions and cross-Scope eligibility. Types can express much of the structural choice but cannot infer arbitrary workflow semantics from open vocabulary.
3. **Naming/conversion:** mutable zero/many keys versus current Memory CLI permanent ID/content-derived key behavior; exact legacy mapping, release/repoint/restoration and surface inventory remain explicit product decisions.
4. **Memory exposure and compatibility:** always-write remember, full-record JSON/Go/HTTP list, prime no-injection, universal bulk postures and safe terminal rendering need actual aligned command/interface contracts.
5. **History/interchange prerequisites:** a complete Memory product needs deliberately composed History plus resolved shared Transfer contracts. Do not award these from endpoint pins, optional projection, an owned capture, batch atomicity, a schema or a current-only partial deployment.
