# Installed Transactional alias boundaries

One NEW case runs the existing ordinary installed launcher against local
packages clean-built and offline-packed from
`b4f895ec77a30b15764948dc6daac439bcbdde0f`. Its explicit fixture contains two
Bead/Link Type descriptors and schemas, two principals, and the actual operation,
Snapshot, changefeed and Event targets. The test compares every installed server
JavaScript module and the installed protocol schema with the clean source build,
then binds the authentic ordinary ready/configuration identity and fixture bytes.
There are no clock, policy, owner or outcome seams and no production changes.

A malformed batch containing a create followed by `putAlias` returns 400
`malformed-request`. Reads find neither the Bead nor alias. A valid three-Resource
batch with that SAME key then succeeds first-time, proving the rejected carrier
neither partially created state nor bound the key. The receiving syntax response
is retained verbatim, including its absent context fields; this case does not
qualify generic receiving-refusal header semantics. Subsequent owner reads and
receipts require nonempty, stable epoch/view and the exact expected position.

The case checks complete, closed one-entry alias receipts for put, repoint and
delete; equal-key replies are byte-identical. A changed put body conflicts with
409 `idempotency-conflict`. An old successful put replay after repoint returns
its old receipt without repointing the locator again. Redirects use 307 with the
exact canonical target, and deletion leaves uniform 404. Alias receipts omit
`effectPosition`, Resource postimages and allocation identities.

The Bead and Link streams of two real Snapshots equal the complete seeded
Resources, including unchanged revisions, metadata and endpoints. Their
checkpoints remain equal, and the original retained Snapshot remains byte-exact.
The full genesis changefeed and Scope Event page stay byte-identical; the
post-Snapshot feed remains the literal empty response. All owner observations
stay at the single Resource batch's `pos-1`. These are actual HTTP observations,
not a mirrored in-memory Snapshot oracle.

Attempt 1 failed before ready because the new Link descriptor omitted required
source/target constraints. Attempt 2 reached the expected malformed response,
but the new generic helper incorrectly required owner context on that syntax
probe. Both failures and exact source snapshots remain retained. Only this
failed NEW case was rerun after those fixture corrections; attempt 3 passed
(29 HTTP exchanges, 242 ms, outer 0.623 s). No old passed test was replayed.
The successful child closed with EOF on both streams and was reaped; the
outer process group was absent and the temporary store was removed.

This finite case addresses the three alias rows' active core branches. Pending
joins, finer race/status permutations, alias receipt expiry, restart/failover and
History-specific authorization are not qualified here. The existing launcher's
startup failure observation does not expose the child's private startup cause;
the first failure's invalid descriptor is established by the exact schema and
successful corrected fixture, not an invented server error transcript. No
retained-history permission or broader profile claim is inferred.
