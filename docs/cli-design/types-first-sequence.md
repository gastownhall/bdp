# First Types acceptance sequence

Donna's October 28 sequence is the first local authoring/use acceptance spine. Complete the first four steps before update, delete or user-created refinement chains. Donna subsequently selected a deliberately temporary, easily replaced placeholder for step 5 while its broader design is discussed. The [canonical CLI](bdp-cli.md) owns shared parsing; the [Types companion](types-cli.md) owns presentation. This is a specification acceptance plan, not a transcript from a qualified executable.

## Establish the explicit baseline

Use one identified Scope and pinned build. Establish actual Types semantics, complete exact definition access, the admitted intrinsic graph and eligible exact metatype defaults through explicit trusted provisioning. Record actual canonical identities and aliases; the labels `type`, `bead-type` and `refines` below are explanatory inputs until their real resolution is established. Do not create a fixture that silently auto-registers definitions or selects defaults.

The [intrinsic publication](../../specs/profiles/types/intrinsic-publication.md) does not supply a live owning Scope. Before claiming the first ordinary `show`, establish an actual ordinary owning route, or select an explicit retained-definition inspection mapping that keeps its interpreting context and wrapper. The current narrow lookup is distinct from ordinary `show`; public spelling for that inspection remains unresolved. Likewise, foreign retained intrinsic definitions are not automatically local graph records. This is a concrete correspondence gap, not permission to change ownership or relabel available-Type inventory as ordinary graph inventory.

## Execute the sequence

| Order | Command / explicit transition | Required observable outcome |
| --- | --- | --- |
| 1 | `bd show TYPE-ID-FOR-BEAD-TYPE`; `bd show TYPE-ID-FOR-LINK-TYPE`; `bd show TYPE-ID-FOR-REFINES-TYPE`; `bd show TYPE-ID-FOR-TYPE` | Inspect each actual definition and its exact own affiliation, descriptor and recorded owned declarations through its established ordinary owning route. For every case using retained-definition inspection instead, preserve the explicit interpreting Scope and complete definition/origin wrapper and identify that different operation honestly. |
| 2 | `bd list --type type`; `bd list --type bead-type`; `bd list --type link-type` | The all-Type family view includes locally owned definitions affiliated with BeadType/LinkType or their admitted refinements. The filtered views follow each definition Bead's own affiliation. Intrinsic records appear only if this Scope actually owns them; retained foreign copies are not local graph records. Abstract Type is a valid family filter, not a valid direct instance affiliation. If none are local, an empty result is truthful and does not prove registration absent. |
| 3 | `bd link list --type refines` | Return the ordinary local Refines family under shared paging/visibility rules. Retained declarations captured in foreign definition editions are not newly local incident Links. Keep the two views distinct. |
| 4 | `bd create --id Foo --type bead-type ...` | Create one local definition Bead with an explicit properties schema. Its own affiliation pins the admitted exact BeadType default. Read it back completely; storing it does not register Foo or choose its default. |
| 5 | `bd create --id X --type Foo ...` — temporary placeholder | Deliberately disposable demonstration while the broader authoring/use design is discussed. Isolate any shortcut so it is easy to replace. It is not specification conformance, registration/default selection or proof of the real instance-creation path. |

For category interpretation, the intrinsic Type, BeadType and LinkType definition
records affiliate with BeadType; Refines affiliates with LinkType. These facts
illustrate the filters; they do not require those foreign intrinsic records to
appear in this Scope's ordinary local lists.

Step 5 does not select automatic registration or a new default policy. The accepted
Types rules remain literal: real use requires exact registration; unpinned use also
requires an explicit eligible default, and a pin avoids only default selection.
Those mechanisms are not today's placeholder implementation assignment.

The commands leave property payloads as `...` until the complete example schema and
actual CLI lowering are supplied; they are not copy-and-run examples with hidden inputs.

## Later real instance acceptance (beyond the placeholder)

Read X back with its exact affiliation and unchanged permitted properties. `bd list --type Foo` must find it through the applicable family contract. Submit an invalid X candidate against the same Foo schema and verify atomic refusal: no created Resource, induced owner change or success Event. A schema shape check alone does not establish this provider result.

Only after that spine is complete, proceed to ordinary property updates, explicit retyping, deletion and user-authored refinement chains. Add one tightening child and prove both inherited validation and family matching; preserve exact target revisions and historical owned declarations. Do not count bootstrap declarations as execution of that later authoring story.

The remaining first-four gaps include intrinsic ordinary/retained inspection mapping and actual implementation. Registration/default-selection operations and real instance admission belong to the later step-5 design. The temporary stub must not be counted as closing those gaps or as an end-to-end conformance result.
