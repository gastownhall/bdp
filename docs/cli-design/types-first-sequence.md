# First Types acceptance sequence

Donna's October 28 sequence is the first local authoring/use acceptance spine. Complete the first four steps before update, delete or user-created refinement chains. Donna subsequently selected a deliberately temporary, easily replaced placeholder for step 5 while its broader design is discussed. The [canonical CLI](bdp-cli.md) owns shared parsing; the [Types companion](types-cli.md) owns presentation. This is a specification acceptance plan, not a transcript from a qualified executable.

## Establish the explicit baseline

Use one identified Scope and pinned build. Establish actual Types semantics, complete exact definition access, the admitted intrinsic graph and eligible exact metatype defaults through explicit trusted provisioning. Record actual canonical identities and aliases; the labels `type`, `bead-type` and `refines` below are explanatory inputs until their real resolution is established. Do not create a fixture that silently auto-registers definitions or selects defaults.

Donna selected real local definition Beads for this sequence, with global identity common and intrinsic to the protocol; packs and aliasing remain deferred. Follow the [intrinsic-only materialization contract](../../specs/profiles/types/types.md#24-ordinary-local-records-for-shared-intrinsic-definitions): the four `TYPE-ID-FOR-*` placeholders below are actual local Resource IDs supplied by trusted initialization, not the shared publication IDs. Preserve the checked exact local/global correspondence and real local ownership. The shared publication remains unchanged and records no original authoring Scope. Its narrow exact lookup remains a different operation with a complete wrapper; do not substitute it for these ordinary shows. Durable native mapping, producer/read implementation and any full Types1 transport carrier are still explicit implementation/source gates.

For category interpretation, the intrinsic Type, BeadType and LinkType definition
records affiliate with BeadType; Refines affiliates with LinkType. These facts
illustrate the filters. This sequence requires their actual local materializations;
it does not relabel the foreign publication records as local graph members.

Step 5 does not select automatic registration or a new default policy. The accepted
Types rules remain literal: real use requires exact registration; unpinned use also
requires an explicit eligible default, and a pin avoids only default selection.
Those mechanisms are not today's placeholder implementation assignment.

The commands leave property payloads as `...` until the complete example schema and
actual CLI lowering are supplied; they are not copy-and-run examples with hidden inputs.

## Later real instance acceptance (beyond the placeholder)

Read X back with its exact affiliation and unchanged permitted properties. `bd list --type Foo` must find it through the applicable family contract. Submit an invalid X candidate against the same Foo schema and verify atomic refusal: no created Resource, induced owner change or success Event. A schema shape check alone does not establish this provider result.

Only after that spine is complete, proceed to ordinary property updates, explicit retyping, deletion and user-authored refinement chains. Add one tightening child and prove both inherited validation and family matching; preserve exact target revisions and historical owned declarations. Do not count bootstrap declarations as execution of that later authoring story.

The local-record direction is settled. The remaining first-four gaps include concrete durable exact correspondence, trusted atomic local allocation/capture and actual command/provider implementation; full Types1 transport additionally requires an explicit selected mapping carrier. The temporary stub must not be counted as closing those gaps or as an end-to-end conformance result.
