## Findings

**1. Two authored execution obligations give conflicting outcomes for the same request shape (quantifier short circuit vs. required-acquisition failure). Severity: medium.**
Location: `specs/profiles/core/query.md:232-235`; `docs/cli-design/query-ir/cases.json:4638` (`any-short-circuit-witness`) and `:4670` (`authorization-relative-count-and-closure`).
Impact: `query.md:233-234` permits ("Valid definitive short-circuit answers do not require unrelated enumeration to finish"), it does not require, a definitive short circuit; `:232-233` makes required unavailable data a failure only "whenever it prevents the answer from being established"; and the MUST at `:234-235` bans only *conflicting successful answers*. Failure scenario: `any` over `walk(A, outgoing, depth 1)` under `contextOverrides.hiddenIdentities = ["…/B"]` with a test satisfied by `LX`→`D` and requiring endpoint content for `L1`/`L5`→`B`. A service that reaches `LX` first returns `true`; a service that reaches `L1` first hits a required acquisition it cannot complete and refuses with `required-acquisition-unavailable`. Both are conformant under the current text, so success and refusal are both "correct" for one request against one Authorization View, and no authored case can state an expected outcome (the obligation says only "true *may* be definitive"). This is the unresolved intersection of two fixed rulings, not a redesign request.
Fix: add one sentence in the Quantifiers section stating precedence — either "a definitive witness/counterexample, once established, MUST be returned even if another branch's required content is unavailable" or "either outcome is conformant; services MUST NOT be required to seek a witness past a required-acquisition failure" — and add one authored case over fixture `constraints` with `hiddenIdentities: ["…/B"]` pinning that outcome.

**2. `protected-projection` is Resource-kind-blind, so a conformant Bead-collection mask is statically refused. Severity: medium.**
Location: `docs/cli-design/query-ir/validate.py:146`; contradicts `specs/profiles/core/resource-projection.md:39-40` ("whole source/target References **on Links**"), `:48` ("an absent omission changes nothing"), `:54` ("Ordinary missing optional data is nonfatal").
Impact: the check tests `segments[0] in {"id","type","revision","source","target"}` without consulting the selection's kind, which `collection_kind(request["selection"], {})` at `validate.py:136` already computes and discards. Failure scenario: `{profile:"list", selection:{op:"scan",collection:"beads"}, result:{form:"resources"}, projection:{omit:["/source"]}}` is refused with `protected-projection`, although fixture Bead records (`fixtures.json` `constraints.beads`) have no `source`/`target` member at all, so per `resource-projection.md:48,54` this is an ordinary absent omission that changes nothing. The converse, Link Reference protection, is never exercised: no case in the corpus combines a `links` selection with a projection, even though `resource-projection.md:98` lists "Link Reference protection" as required coverage.
Fix: bind the kind (`kind = collection_kind(request["selection"], {})`) and gate `{"source","target"}` on `kind == "links"`, keeping `{"id","type","revision"}` protected for both kinds; add two cases — `scan links` + `omit:["/source"]` → `protected-projection`, and `scan beads` + `omit:["/source"]` → accept.

**3. The CLI correspondence document asserts sorting "retains" a shared carrier and never names the accepted one-pointer amendment or its pending carrier. Severity: medium-low.**
Location: `docs/cli-design/query-ir.md:203-204`; diverges from `specs/profiles/core/query.md:272-275` and from the finding-15 disposition at `review/README.md:29` ("do not imply current native support").
Impact: `query.md:273-275` is careful — authority-advertised `order` is the baseline, per-request sorting "needs an explicit protocol/discovery/carrier amendment", and "This AST schema does not assign that common control a wire member". `query-ir.md:204` collapses sorting with continuation into "Sorting and continuation retain their shared carriers", which reads as though request sorting already has a carrier; `query-ir.md:242` then says sorting details remain integration work, so the explainer contradicts itself. Failure scenario: a CLI implementer reading only `query-ir.md` (the document scoped to CLI correspondence, which contains no other mention of sort and no `--sort` flag) concludes per-request sorting is already carried and needs no amendment. Grep confirms no `--sort` spelling exists anywhere in `docs/` or `specs/profiles/core/`, so the sentence is the only sorting signal in that document.
Fix: replace `query-ir.md:203-204` with the `query.md:272-275` formulation — continuation retains its declared carrier; authority `order` is the retained baseline; the selected one-pointer request sort applies to full selected data before projection and is pending an explicit protocol/discovery/carrier amendment that this AST does not assign.

**4. `any` mandates the dead binder that finding 21 made a refusal for `walk`. Severity: low-medium.**
Location: `docs/cli-design/query-ir/query.schema.json:413-417` (`any.required` includes `bind`, `predicate` optional) vs `:619-626` (`walk` `dependentRequired` both ways); `validate.py:64`; cases `any-without-test` (`cases.json:1235`) and `any-empty-false` (`:1291`).
Impact: `walk` with `bind` and no `through` is a schema refusal (`binding-without-through-refuses` → `invalid-ast`), on the finding-21 rationale that an unreferenceable binder is dead. `any` with `bind` and no `predicate` is the identical shape and is accepted: in `any-without-test` the `any` node declares `bind:"r"` which nothing can reference, because the surface alias in `query-ir.md:142-144` is consumed by the walk's `through`, not by `any`. Failure scenario: a client emitting the surface form at `query-ir.md:153` ("`any` can omit its test") must invent an arbitrary unused binder name to pass validation, and two structurally identical dead-binder defects get opposite admission verdicts.
Fix: either (a) drop `bind` from `any.required` and add `"dependentRequired": {"predicate": ["bind"], "bind": ["predicate"]}`, change `validate.py:64` to `predicate.get("bind", "__unused")` (mirroring the `walk` handling at `:86`; a bare removal would raise `KeyError` instead of `AdmissionError`), and drop `bind` from the two accepted cases plus add a `bind`-without-`predicate` refusal case; or (b) add one sentence to `query.md:220-222` recording that `any`'s binder stays declared even with the test omitted, deliberately unlike `walk`.

**5. The Graph profile's Link Type test is described as required in the explainer but is optional in the normative table and in the corpus. Severity: low.**
Location: `docs/cli-design/query-ir.md:18` ("roots → walk with a Type restriction → graph") and `:198-199` ("The initial graph profile restricts the walk by Link Type"); vs `specs/profiles/core/query.md:284` ("optional single exact/family Link Type test") and `validate.py:158-159` (which admits `through` absent via `predicate is True`).
Impact: two `profile:"graph"` cases are admitted with no `through` at all (`external-graph-formation-refuses`, `mixed-visible-hidden-roots-refuse`). Failure scenario: a Graph-only implementor following `query-ir.md:198` rejects a `through`-less rooted walk that the profile admits and that the case ledger expects to reach runtime, producing a false `outside-profile` refusal.
Fix: change both spots to "optional Link Type restriction" to match `query.md:284`.

**6. An empty `projection` object is admitted, so a maskless `graph` request is refused on a serialization artifact. Severity: low.**
Location: `query.schema.json:37-60` (`projection` has `"required": []`, no `minProperties`); `validate.py:140` (`require("projection" not in request, "graph-projection-undefined")`).
Impact: `resource-projection.md:33` makes "no includes or omissions" equal the full representation, and `:37-38` requires supplied mask arrays to be nonempty ("omit an array member to request no mask of that kind"). The schema still accepts `"projection": {}`. Failure scenario: a generated client that always emits the `projection` member gets `{profile:"graph", …, result:{form:"graph"}, projection:{}}` refused with `graph-projection-undefined`, while the byte-identical request minus the empty member is admitted — a mask-free request refused for requesting no mask.
Fix: add `"minProperties": 1` to `projection` in the schema (mirroring the nonempty-array rule), or test for a non-empty mask in the graph check; add one `reject-schema` case for `projection: {}`.

**7. Include-mode masks may slice a protected Reference; omit-mode and the plane rule both refuse the analogous shape. Severity: low.**
Location: `validate.py:146-147`; `resource-projection.md:39-40` ("A mask cannot misrepresent their meaning") and `:46` ("References stay whole").
Impact: `unsupported-plane-mask` refuses `len(segments) > 1` for `revisionProvenance`/`ownedLinks`/`links` in both modes, and `protected-projection` catches `omit:["/source/uri"]` through its first segment, but `include:["/source/uri"]` or `include:["/type/uri"]` passes. Failure scenario: `{profile:"list", selection:{op:"scan",collection:"links"}, projection:{include:["/source/uri"]}}` is admitted; its only two readings are "redundant, protected context is unioned whole anyway" (`resource-projection.md:34`) or "emit a sliced Reference", which `:46` forbids. Nested paths under `/id`, `/revision`, `/type` are likewise meaningless on the logical shape.
Fix: add `require(not (segments[0] in {"id","type","revision","source","target"} and len(segments) > 1), "unsupported-plane-mask")` alongside the existing plane check, applied to both modes; add one refusal case.

**8. List admits `member` in both operand directions but `contains` in only one, with no normative sentence for the asymmetry. Severity: low.**
Location: `validate.py:129-132`; `specs/profiles/core/query.md:287-295`.
Impact: `query.md:293-295` fixes membership explicitly in both directions (finding 9), and `:289` admits "literal comparison operands" generally, but `local_predicate` requires specifically `expr["substring"]["op"] == "literal"`. Failure scenario: `{profile:"list", selection:{op:"filter", input:{op:"scan",collection:"beads"}, bind:"b", predicate:{op:"contains", text:{op:"literal",value:"platform-core"}, substring:{op:"field", of:{op:"binding",name:"b"}, path:["properties","team"]}}}}` is refused with `outside-profile` although both operands are local-or-literal, exactly the shape membership admits. The restriction may well be intended, but it is unstated, so the checker is stricter than the profile text it implements.
Fix: add one clause after `query.md:295` ("List's `contains` requires the literal substring operand; the mirrored form is outside this initial subset"), or admit the mirrored form as `member` does; either way add one case fixing the verdict.
